## 1. The question, and when it has to be answered

Today mpv draws into a native child window that Sublore creates under the Tauri toplevel and hands to mpv as its `wid` option. The alternative is libmpv's render API, where mpv hands us frames and the application draws them itself into a surface it owns. The question is narrow and stays inside CLAUDE.md §2: libmpv remains the video engine, Tauri remains the shell, nothing about the stack is being reopened. What is being decided is only the path by which a decoded frame becomes pixels the user sees, and therefore what may and may not be drawn near that frame.

It has to be decided before M2.0 starts. M2.0's T3 builds a layer registry whose entire purpose is to hide the native surface whenever an HTML layer opens (`docs/design/m2-0-tasks.md:116-129`, `:502-513`), which is decision 1, which exists only because a native child window cannot be drawn over. If the render API is coming, that registry is built to serve a constraint about to be deleted. It also has to be decided before MW: MW.1's acceptance criterion is the full suite green on Windows with the same spec files and the same assertions as on Linux (`BACKLOG.md:198-199`), and a migration changes what those assertions are on both platforms at once. MW gates release (`BACKLOG.md:205`), so a decision taken late is paid for twice.

## 2. What we do today, and what it has cost

At Tauri setup, `video::setup` creates a GDK child window under the toplevel, forces it native with `gdk_window_ensure_native` so it has a real X11 id, and passes that id to `Player::new` before any mpv core exists (`src-tauri/src/video/surface/linux.rs:16-60`, `src-tauri/src/video/mod.rs:119-141`). The player sets it as mpv's `wid` inside the initialiser, and on Linux pins `gpu-context=x11egl` beside it (`player.rs:186-192`). mpv then creates its own window inside ours: the installed mpv 0.41.0 manual says that on X11 mpv "always creates its own window, and sets the wid window as parent", and that window is what the harness treats as the honest attachment signal (`docs/reports/n2-probe.md`). Sublore never sees a frame.

The surface handle stays on the main thread in a thread-local and is never shared (`video/mod.rs:25-32`). Visibility is derived, not set: one `SurfaceState` holds whether a video is open and whether the last reported rectangle has area, and a single `settle` turns that into show or hide, the only two places in the module that touch the window (`video/mod.rs:36-88`). Geometry comes from the frontend: `VideoStage` measures `.stage__surface` with `getBoundingClientRect` in CSS pixels and coalesces its observers into one report per animation frame, which reaches `apply_region` and, when the rectangle has area, `set_region` (`src/components/VideoStage.tsx`, `video/mod.rs:267-284`). `set_region` also raises the surface, on Linux and on Windows both (`surface/linux.rs:65-66`, `surface/windows.rs:57-73`). Hiding is an unmap, not a destroy, and the surface is torn down only after `Player::shutdown` reports the mpv core actually gone (`video/mod.rs:109-116`).

The whole platform layer is small: 1,197 lines across the six files of `src-tauri/src/video/`, of which the two platform backends are 85 and 98 lines (measured with `wc -l`). mpv owns A/V sync, seeking, hardware decode with CPU fallback, container and codec support, subtitle rendering and filters, and the application's entire contract with it is a short option list, two observed properties and a handful of IPC commands.

This approach has produced the following. Each item is either a measurement with its report named, or a reading of source with its lines named; none of it is inference:

**The whole application is forced onto X11.** `main.rs` sets `GDK_BACKEND=x11` before GTK picks a backend, and its own comment says why: mpv's `--wid` needs an X11 window id and the Wayland VO has no equivalent (`src-tauri/src/main.rs:33-38`). This is not a video decision, it is an application-wide one. On every Wayland desktop Sublore is an XWayland client, interface included.

**N2b: mpv drew past the window it was handed.** With a Wayland display in the environment, mpv's `gpu-context=auto` chose Wayland and the surface reported `IsViewable` with zero children while the transport reported playback over nothing. Measured, then fixed by pinning `x11egl`: 0 child windows and 0 saturation without the option, 1 child and 98.4 saturation with it (`docs/reports/n2b-probe.md`), and three launches out of three showing colour bars on the owner's own Wayland session (`docs/reports/n2b-collaudo-reale.md`). The bug was an implementation bug and it is fixed. The constraint behind it is not: forcing the whole app onto X11 is the price of the mechanism, not of the bug.

**N2c: the surface lands in the wrong place at fractional scale.** On the owner's 3840x2160 display at scale 1.5 the video plays at 395x120 over the transcription bar instead of covering the stage (`docs/reports/n2b-collaudo-reale.md` §3, filed as `BACKLOG.md` N2c). One correction belongs here, because two documents state the mechanism wrongly and M2.0 will read them: the report and the N2c entry both say `apply_region` multiplies the rectangle by `window.scale_factor()`. That describes the Windows path only. On Linux, `set_region` calls `region.logical()`, which is `scaled(1.0)`, so the scale factor is discarded and the CSS rectangle goes into GDK unchanged (`surface/linux.rs:62-67`, `surface/mod.rs:44-47`, against `surface/windows.rs:57-59`). Whatever causes N2c, it is not that multiplication, and N2c's second acceptance criterion — a unit test of the coordinate conversion at fractional factors — would pin arithmetic the Linux path does not reach through that input.

**A shipped design compromise.** N1's close gate is a native three-button dialog rather than an HTML one, chosen for the stated reason that an HTML dialog would sit behind the video (`BACKLOG.md`, N1 status line).

**Decision 1 itself.** The product rule is that the picture disappears whenever any HTML layer opens, including layers that do not overlap the video rectangle at all (`docs/design/decisions.md` §1, `docs/design/shell-layout.md:141`). That is not a fix for occlusion, it is an accommodation of it.

**A second visibility state machine that has to be kept true by hand.** Gate 1 found the surface visible at startup with no video — an opaque slab over the empty stage — introduced by a fix written under review pressure (`BACKLOG.md`, N2 gate 1 entry). The machine that now prevents it is `video/mod.rs:36-88`, and `e2e/specs/video-empty.spec.js` exists specifically to stop that regression coming back.

**Verification is expensive and partly impossible in CI.** The application cannot read back its own frame, so the only proof the picture is on screen is an external capture. Under Xvfb with llvmpipe the frame appeared 2 times in 10 while mpv was attached 10 times out of 10, which is why `video-surface.spec.js` asserts map state and mpv's child window and deliberately not pixels (`e2e/specs/video-surface.spec.js:1-16`, `docs/reports/n2b-collaudo-reale.md` §5). There is no working pixel assertion in the suite today: `e2e/lib/pixels.js` exports a saturation helper that no spec imports, and `wdio.conf.js` imports only `requireFfmpeg` (measured by grep). Every frame-presence verdict in this repo so far came from a hand-run probe or the real-session script.

**N1b, on current evidence, is not the surface's fault, and it is still open.** The crashing frame is inside `_gdk_x11_display_queue_events` during teardown after the close gate saves, with no Sublore frame above `run()`, and the report files it against N1 (`docs/reports/n1b-segfault-uscita.md`). That report has since been amended in the working tree: the second GTK thread rfd starts was present in the earlier cores and is **not** what makes the crash, so the lead it once carried is refuted. The attempted fix moved the gate's dialogs onto the main thread through the new `src-tauri/src/dialog.rs`, and the 30-run battery in `docs/reports/n1b-trenta-corse.md` still produced one SIGSEGV on the save branch plus four unexplained non-crash failures. The battery's own conclusion is the one to quote: the rate went from 1 in 12 to 1 in 30 and **that is not evidence that it moved**, because at the old rate one crash or fewer in 30 comes up about a quarter of the time. So the number to carry forward is "measured, still crashing, rate unknown", not a rate.

N1c belongs beside it: the file picker still goes through the plugin's blocking pickers (`project/mod.rs:245-257`), so rfd's permanent GTK-iterating thread is still armed for the rest of any session that opens a project, and rfd 0.17.2 offers no way to stop it. Both are listed here only because any change to teardown ordering lands on top of them, and a render context that must be freed on the thread holding the GL context is exactly such a change.

Three documents M2.0 will be built from cite code that no longer exists, and they are stale in two different ways. `docs/design/decisions.md:21`, `docs/design/shell-layout.md:149` and `docs/design/post-v1-plan.md:258` all point at an unconditional `show()` inside `video_open` at `video/mod.rs:106`; after commit `d224f3c` that line is inside `VideoState::player`, and the belt-and-braces argument in shell-layout rests on a call that is gone. Separately, `shell-layout.md:147` cites `video/mod.rs:196-197` for the cleanup path that reports an empty region, and those two lines today are inside `video_open`'s failed-open compensation, not inside anything a cleanup reaches. Reports carrying the same citations (`n2-probe.md:7`) are dated records and can stay as they are; the three design documents cannot, because M2.0 reads them as current. Worth correcting whichever way this decision goes.

## 3. The alternative, described well enough to start from

Under libmpv's render API the application creates a render context against the mpv core and renders frames itself. The rules below are quoted from the headers installed on this machine (`/usr/include/mpv/render.h`, `render_gl.h`, `client.h`; mpv-libs 0.41.0-5.fc44, `MPV_CLIENT_API_VERSION` 2.5 at `client.h:251`). They are byte-identical to the copies vendored by `libmpv2-sys` 4.0.1, which is what the pinned crate actually compiles against: `cmp` reports no difference on all three files against `~/.cargo/registry/src/*/libmpv2-sys-4.0.1/include/`.

The context has to exist before mpv creates a video output: "The renderer needs to be created with mpv_render_context_create() before you start playback (or otherwise cause a VO to be created)", and without it "Video initialization will fail ... or it will revert to a VO that creates its own window" (`render.h:32-36`, `:113-115`). Loading a file is one way to create a VO; `--force-window` is another. Only one context can exist per core, and it must be freed before the core is destroyed or the behaviour is undefined (`render.h:117`, `:122-123`).

There are two backends and only two: OpenGL and software (`render.h`, "Supported backends"). With the OpenGL backend, for all `mpv_render_*` functions "the OpenGL context must be 'current' in the calling thread, and it must be the same OpenGL context as the mpv_render_context was created with. Otherwise, undefined behavior will occur" (`render.h:67-70`). That rule binds teardown too, since `mpv_render_context_free` is one of those functions and nothing in its own documentation exempts it; `render_gl.h` states that all `mpv_render_*` APIs implicitly use the GL context unless specified otherwise. The one documented exception is `mpv_render_context_set_update_callback`, which may be called from any thread and touches no GL (`render.h:625-626`).

mpv supplies no GL loader for this path: "libmpv will not normally attempt to resolve GL functions on its own, nor does it link to GL libraries directly", and reaches OpenGL only through the `get_proc_address` callback the embedder provides (`render_gl.h:107-123`). That is a statement about the render API. It is not true of the current path: under `wid`, mpv selects and drives its own context, and Fedora's `libmpv.so.2` carries `libGL.so.1`, `libEGL.so.1` and `libwayland-egl.so.1` as its own `DT_NEEDED` entries (`readelf -d`, so this is direct linkage and not a transitive one inherited through `ldd`). Adopting the render API therefore moves the GL context and the loader from mpv into Sublore.

The redraw contract is: mpv calls the update callback, that callback may call no mpv API at all and can only wake the render thread, and the render thread calls `mpv_render_context_render`. `mpv_render_context_update` is optional in the default configuration and becomes mandatory after every update callback only if `MPV_RENDER_PARAM_ADVANCED_CONTROL` is set; its return value is a bitset to be masked, not compared (`render.h:621-673`). `mpv_render_context_render` blocks until the frame's target display time unless the embedder disables it, bounded by `--video-timing-offset`, whose default on the installed mpv is 0.050 s (`render.h:301-317`, `:536-541`; `man mpv`). `ADVANCED_CONTROL` is not a free performance switch: it is a promise that the render thread never waits on the core, and "If you ignore this requirement, deadlocks can happen, which are made non-fatal with timeouts; then playback quality will be degraded, and the message `mpv_render_context_render() not being called or stuck.` is logged", while with the flag set "a real deadlock will freeze the mpv core thread forever" (`render.h:76-82`).

Hardware decoding through this API keeps its per-platform requirements and moves them into our code: ANGLE on Windows, EGL plus the native display resource on Intel/Linux, GLX or EGL on nVidia/Linux, CGL on macOS (`render_gl.h:88-97`).

The software backend is not a fallback for this product. Its own header says so: "an extremely simple (but slow) renderer to memory surfaces. You probably don't want to use this", and "everything, including color conversion, scaling, and OSD rendering, is done on the CPU, single-threaded. In particular, large video or display sizes, as well as presence of OSD or subtitles can make it too slow for realtime" (`render.h:125-145`). Subtitles on the frame is decision 7, so that warning names our shipping case rather than an edge case. It is also unreachable from the pinned crate: `libmpv2` 6.0.0's `RenderParamApiType` has the single variant `OpenGl` and its `RenderParam` stops at `SkipRendering`, with none of the SW size, format, stride or pointer parameters (verified in the vendored source). Reaching the SW path means raw `libmpv2-sys` or a fork.

Two facts about the dependency as it stands. `src-tauri/Cargo.toml:30` declares `libmpv2` with `default-features = false`, and `render` is the crate's only default feature, gating `pub mod render` — so the wrapper is not compiled into Sublore at all today (verified in the crate's manifest and `src/mpv.rs`). And `create_render_context` borrows the `Mpv`, while `Player` holds an `Arc<Mpv>` it clones into command threads (`player.rs:166`), so the context cannot simply be stored beside the core.

The part nobody has answered is where the frame lands. The render API writes into a framebuffer the embedder owns. In a Tauri window on Linux that framebuffer would belong to a GTK widget, and Tauri exposes enough of the hierarchy to attempt it — `gtk_window()` and `default_vbox()` are public — but a `GtkBox` cannot overlap children, so the webview would have to be re-parented into an overlay container, which depends on wry's internal layout rather than on any documented promise. On Windows the host is not a GTK widget at all, so that platform needs its own design. Nothing in the headers or in Tauri's API says how a GL surface composites against WebKitGTK, WebView2 or WKWebView inside a Tauri window. That is the spike in §7, and until it runs, the render API's benefit for decision 1 is a hypothesis, not a property.

## 4. What the alternative would cost

**Rust.** The two platform backends exist only to create and place a native window and to produce a `wid`; both would be replaced (`surface/linux.rs`, 85 lines; `surface/windows.rs`, 98 lines). `surface/mod.rs`'s region arithmetic would change shape, since a render target's size is not an X11 rectangle clamped to 16 bits. The visibility machine in `video/mod.rs:36-88` survives as a decision — the render API has its own per-frame "do not draw" control, `MPV_RENDER_PARAM_SKIP_RENDERING` (`render.h:319-333`) — but its enforcement point moves and the two `show`/`hide` leaf calls go. `PlayerConfig::embedded` and the two option lines it drives are replaced by render-context creation after the core exists, plus a `vo` selection. `Player::shutdown`, which already drains for up to five seconds to report whether mpv is really gone (`player.rs:348-390`), gains a second ordering obligation: free the render context first, on the thread holding the GL context.

**Frontend.** `VideoStage` stops reporting a rectangle for a native window and starts sizing a render target; `useVideoPlayer`'s region command and `src/types/video.ts`'s "zero hides the surface" contract change with it.

**Tests.** The 14 Rust tests in `src-tauri/tests/video_playback.rs` run headless with `vo=null` and would survive nearly untouched — which is also the point: they prove nothing about anything reaching the screen. There is no `#[cfg(test)]` module anywhere under `src-tauri/src/video/` (verified). Seven of the suite's 33 guarded E2E checks rest entirely on X11 child-window structure and would need new assertions: `video.spec.js`'s "sizes the native video surface over the stage", the three tests in `video-surface.spec.js`, and the three in `video-empty.spec.js` (counted). Two of `wayland-attach-check.js`'s four guarded checks are structural and would go, tripping its `EXPECTED_CHECKS = 4` guard, which treats a removed assertion as a failure.

Three of those assertions have no like-for-like replacement. The geometry check finds a direct child of the toplevel whose X11 rectangle matches the DOM rectangle within 2 px; with no such window, "the video is in the right place" can only be answered by capturing pixels and comparing where colour appears against the DOM rectangle. The ten-cycle leak check counts native child windows; a leaked render context, FBO or texture is invisible to `xwininfo`. And `video-empty.spec.js` catches "an opaque slab covers the empty stage" by asserting `IsUnMapped`; under a render path the same regression becomes "we painted a black rectangle over the placeholder", which is a pixel question.

**Harness capability that does not exist today.** Per-window pixel capture on Linux, and a second implementation on Windows. A negative control that refuses rather than returning a number when nothing is drawing. A display where presentation is trustworthy, since the instrument the migration would depend on is measured unreliable on the one CI uses. This is the largest hidden cost, and it is a cost the current approach avoids by being externally observable with `xwininfo` and no instrumentation inside the app.

**Milestones.** M2.0 waits, and M2.0 blocks M2.4 through M2.6 (`BACKLOG.md:115`). MW waits and is partly re-specified, and MW gates v1.0 and any sale (`BACKLOG.md:205`, CLAUDE.md platform policy). N2c's behavioural half becomes largely moot, since the fix lives in `apply_region`; doing it first and migrating later throws that work away, though its unit-test criterion is worth keeping either way. N1b sits in the same teardown code and would be joined there by a GL-context ordering rule.

**Size, stated as an estimate and not a measurement.** Roughly eleven to fourteen backlog-sized tasks: one spike for compositing, two Linux target-surface tasks, two Windows, two player-lifecycle, one or two for the state machine and IPC and frontend, two or three harness tasks, and one measurement task against the CLAUDE.md §7 budgets. That is larger than M2.0's ten-task decomposition, and it delivers no new user-visible capability of its own. It also excludes the gate cost, which this repo has measured as real: gate 1 ran three lenses over one task's worth of video-surface work and produced 7 blockers, 15 serious and 25 minor findings, all fixed before the gate opened.

## 5. What each approach forecloses

This is the section that decides, so it is stated as concretely as the evidence allows.

### Keeping the X11 child window forecloses

**Any HTML on the picture, permanently.** Not awkward, impossible while the surface is mapped: on-video transport controls, a hover scrub preview over the frame, an HTML subtitle overlay, a translucent scrim, a drawn selection region, rounded corners or a shadow on the video panel, and any CSS filter on the picture. The mechanism is that the surface is a native X11 child of the toplevel and the webview's pixels are the toplevel's own drawing, so X clips the parent's drawing by its viewable children. Anything that must appear on the frame has to be produced by mpv, which is why decision 7 feeds subtitles to mpv through a shadow-copy file rather than rendering them from application state.

That forecloses M16 entirely, and M16 is the only milestone the post-v1 plan calls genuinely blocked by architecture (`docs/design/post-v1-plan.md:225-235`). Visual typesetting — a crosshair with script coordinates, dragging a position, rotation, scale, crop — needs both drawing on the frame and the mouse on the frame, and neither exists here.

**Mouse events on the frame, unanswered and probably absent.** The surface is `InputOutput` with pass-through disabled and only exposure events selected (`surface/linux.rs:34,44`), mpv's own keyboard and cursor input are off (`player.rs:44-46`), nothing in `VideoStage` handles clicks and no test covers it. Click-to-seek, click-to-focus and drag on the video are all unanswered questions, not shipped behaviour.

**Native Wayland, for the whole application.** `GDK_BACKEND=x11` is set before GTK initialises, so Sublore is an XWayland client on every Wayland desktop. Upstream has not moved on this and shows no sign of doing so, which is as far as the evidence goes: mpv issue 9654, "GUI embedding for Wayland in libmpv", was opened 2021-12-30 and is still open under the labels `down-upstream:wayland` and `meta:feature-request`, and its predecessor, issue 1242 from 2014, is closed carrying `priority:stalled`. Both were read on 2026-08-30. **What I could not find is a maintainer statement, and an earlier draft of this line asserted one.** Neither issue page carried a maintainer verdict that the use case will never be supported, so "upstream has declared this dead" is not available to us; "nobody has implemented it in twelve years and the request sits under a down-upstream label" is, and it is enough for a planning horizon that ends at v1.0. The measured cost of XWayland is already visible here in fractional scaling (N2c). A further cost, presentation timing, is untested in this repo and unsourced in this document; treat it as an assumption, not a finding.

**macOS, on today's mpv.** The installed mpv 0.41.0 manual documents `--wid` for X11, win32 and Android, with no macOS paragraph (read here from `man mpv`), while `client.h` in the same installation still says the method "works on X11, win32, and macOS only" (read here from `/usr/include/mpv/client.h`). mpv's own sources contradict its own header, and the manual is the current one. The gate-2 research traced the removal to the deletion of the Cocoa backend in mpv 0.37.0 and the documentation catching up in 0.40.0; I did not re-fetch that history, so the version numbers are second-hand while the local contradiction is measured. Practically: a macOS port cannot reuse this mechanism, because there is no macOS backend to attach a window handle to. CLAUDE.md forbids designs that block a later macOS port, and this one does — through mpv, not through anything Sublore wrote.

**Clipping the video by a CSS ancestor,** which is why the shell carries a hard rule that the panel holding the video never scrolls (`docs/design/shell-layout.md`, M2.0 acceptance criteria).

**Compositing the app's own UI and the video into one image from inside the webview.** The real-session harness needed an external window capture plus a crop to see both; a webview-side capture would show a hole.

### Moving to the render API forecloses

**External verification with no instrumentation,** which is this repo's cheapest honest signal. Today the E2E suite asserts on the video from outside the process with `xwininfo`: the surface's map state, and mpv's own child window inside it. Both disappear. Everything they proved would move to pixels, on an instrument the repo has measured as unreliable in CI (2 frames in 10 under llvmpipe) and which does not exist yet in either platform's harness.

**mpv owning the hard parts.** A/V sync, presentation timing, the GL context, the loader, and hardware decode setup all move from mpv into Sublore. The render API does not remove platform-specific work, it relocates it: ANGLE on Windows, EGL plus the native display handle on Intel/Linux, CGL on macOS.

**The CPU fallback through the pinned crate.** `libmpv2` 6.0.0's safe API exposes only the OpenGL backend, so a software render path needs raw FFI or a fork, and mpv's own header disqualifies that path for a product that puts subtitles on the frame. CLAUDE.md §2's CPU-fallback rule is written for ASR, not video, but the video rule next to it — if libmpv cannot do it, the feature waits — points the same way.

**A shutdown path that is currently simple to reason about.** Free the context before the core, on the thread where the GL context is current, on top of `Player::shutdown`'s existing drain, on top of N1b and N1c: an intermittent SIGSEGV in GTK teardown that is still open after its first attempted fix and whose rate is not known well enough to quote (§2), plus a second GTK-iterating thread that any project-open still starts. Three unexplained things in the same teardown is already the wrong place to add a fourth ordering rule.

**And, on today's evidence, it does not yet buy decision 1 back.** The render API changes who decides stacking, but the frame still lands in some widget whose relationship to the webview nobody has established. Putting HTML over it needs the webview transparent and composited above our surface, on a machine where WebKitGTK could not allocate through DMABUF at all and the app renders only because the DMABUF renderer is disabled (`docs/reports/n2b-collaudo-reale.md` §1, `main.rs:25-28`). The gate-2 research also reported third-party accounts of transparency failing on similar NVIDIA configurations under exactly that workaround; **I did not re-fetch them, so that is hearsay in this document and is written as hearsay** — it is a reason to run P1, never a reason to skip it. None of it is measured for Sublore, which is the point: the benefit is unproven and the costs above are not.

### One thing that looked like a foreclosure and is not

**A second simultaneous video view** was in the left column of an earlier draft, and it does not belong to either side. There is one surface slot and one player (`video/mod.rs:25-32`, `:100-102`), and that is a limit of the module, not of X11: a render path would need a second render context, a second target and the same lifecycle work, and the header caps it at one context per core (`render.h:117`), so it would want a second core too. Neither approach gives it away free and neither approach is cheaper for it. It is out of v1 scope in any case; it is named here only so nobody counts it as a reason.

### One route that neither section forecloses

There is a third option that moves no pixels and needs no new rendering path: shape the native surface so HTML shows through a hole cut where an overlay sits. The X SHAPE extension is present on the owner's display (measured with `xdpyinfo` on `:0`), GDK binds shape combination, and the Win32 equivalent is `SetWindowRgn`. It buys binary alpha only — no scrim, no antialiased corner, no shadow — and it needs the frontend to report overlay rectangles, which `VideoStage` already does for its own. Whether a parent's bounding shape clips mpv's child window in practice on this driver is untested; it is one of the probes in §7. This is not a recommendation, it is a reason not to treat the choice as binary.

## 6. Recommendation

**Keep the X11 child window for v1.0. Do not start the migration now, and do not build M2.0's layer registry as though it were temporary.**

The reasoning is that the two things the render API would buy are both outside v1. Drawing on the frame and receiving the mouse on the frame are M16, which the plan already places after M14 and behind an explicit owner decision, and both sit after MW in the release order — so the payoff cannot arrive before v1.0 under any ordering the plan allows. Against that, the migration delays M2.0, which blocks M2.4 through M2.6, and delays MW, which gates release and any sale. It replaces a mechanism that is measured working on the primary platform, including the specific behaviour decision 1 depends on, with one whose central question — where the frame lands relative to the webview — has no answer in any source consulted. And it trades an externally observable verification story for one that requires harness capability nobody has built on either platform.

The accommodation this leaves in place is real and should be named rather than glossed: the picture disappears whenever any HTML layer opens. That is a visible product behaviour, not an internal detail. It is cheap, it is one implementation across Windows and Linux, and the re-show it depends on is measured on Linux — though see the probe list, because the paused case is measured more thinly than the playing one.

Three conditions would change this recommendation, and only these three:

1. **The compositing spike (P1) says the render API can put HTML over the frame on the owner's hardware, and the owner's checklist rejects the disappearing picture.** Then the benefit is proven and the cost is a product requirement rather than a preference. Order matters: the probe first, the checklist second, the migration only if both land that way.
2. **A v1-scope feature turns out to need drawing on the frame or the mouse on the frame.** Nothing in §1 of CLAUDE.md does today. If one appears, it is a scope question for the owner before it is an architecture question.
3. **macOS is reactivated before v1.0.** The `wid` mechanism has no macOS implementation in current mpv, so a macOS port replaces the surface layer rather than extending it. Concretely, the recommendation would become: migrate before writing any macOS surface backend, because the alternative is writing a third `wid` backend that mpv cannot serve and then throwing it away. The migration does not get cheaper, but it stops being avoidable, and it should then be sequenced ahead of the macOS work rather than after it. This is the one condition that changes the answer without P1 having to succeed, and it is also the least likely: macOS sits in the parking lot and reactivating it is an owner decision nobody has asked for.

**One thing that is not on that list, and a reader will assume it is.** If P2 fails — if the paused frame does not come back through the product's own hide and show path on real hardware — that does **not** promote the render API. It breaks decision 1, which is a product decision, not an architecture one, and the render API is not its fix: a render path that stops drawing and starts again has the same question to answer and no measurement behind it either. A P2 failure sends the question back to the owner as "the picture cannot be hidden and restored cheaply, so decision 1 needs a different shape", and the shapes on the table are the ones decision 1 already rejected — native menus, separate windows — plus the shaped-surface route in §5. The migration only enters that conversation through condition 1.

Three pieces of work should happen regardless of this decision, because they are true either way.

- **N2c needs P3 before it needs code.** Its second acceptance criterion asks for a unit test of the coordinate conversion at fractional factors, and §2 shows that criterion was written against a mechanism the Linux path does not use. What such a test can honestly assert is narrow and worth having anyway: that `logical()` is scale-independent, that `physical()` scales, and that both clamp at the 16-bit X11 limit. What it cannot do is explain the 395x120 rectangle, because no scale factor is applied on the path that produced it. P3 is the prerequisite; until it runs, N2c has a symptom and no mechanism, and any fix written for it is a guess.
- **The stale citations** of `video/mod.rs:106` in `decisions.md:21`, `shell-layout.md:149` and `post-v1-plan.md:258`, and of `video/mod.rs:196-197` in `shell-layout.md:147`, should be fixed before M2.0 reads them.
- **P9, the pixel instrument**, because the repo currently has one saturation helper that no spec imports and no measured statement about whether it discriminates. That is true whichever mechanism ships.

## 7. What is still unknown, and the cheapest probe for each

The owner's rule is that an alternative is probed, never presumed. Each probe below names what it measures and what each outcome would mean.

**P1 — Does a transparent Tauri window composite over a sibling widget on the owner's machine?** This is the spike the whole render-API case rests on, and it is the one that has to come back with a number rather than an impression.

Build a throwaway Tauri window with `transparent: true`, pack a drawing area filled with a fully saturated colour behind the webview, give the page a transparent background and one opaque HTML element positioned over part of that widget, and capture the window with `import -window <id>` on the owner's real display, with the NVIDIA workarounds of `main.rs:25-28` in force because that is the configuration the product ships. Do not use `x11grab`: it reads black under rootless XWayland (WORKFLOW §4c). No synthetic input is needed at any point, so this probe is allowed on the real display.

Three regions, one instrument. Crop each and read `signalstats` SATAVG the way `real-session-check.mjs:84-95` already does: **A**, the widget under transparent page background; **B**, the widget under the opaque HTML element; **C**, page background over no widget at all. The pass condition is A high, B and C low, on **five runs out of five**, with A at least ten times C — the empty shell measured 2.1 against a colour-bar frame's 5.86 in the real-session check, so a saturated fill against a neutral page should separate far wider than that, and a margin narrower than 10x means the instrument is reading something other than what the probe set up.

A passing result means the compositing route exists on this hardware and the render API could deliver HTML over video. A low everywhere means the transparent window never composited and the answer is no. A high everywhere, including C, means the capture is wrong rather than the app, and the probe is rerun before anything is concluded from it. B high — the widget showing through the opaque element — is the interesting failure: it says compositing works in one direction only, which would foreclose HTML over video just as firmly as no transparency at all. Until this runs, no render-API estimate is worth hardening.

**P2 — Does the paused frame really come back through the product's own hide/show path, on real hardware?** The only pixel evidence is `docs/reports/n2-probe.md`, one run per case, taken at commit `6d6d3ab` before `gpu-context=x11egl` existed, driven with `xdotool` at the X level rather than through `Surface::hide`/`show`, on the Xvfb display later measured as presenting 2 frames in 10. The playing case is sound there: the spread kept advancing after the remap, which preserved pixels cannot explain. The paused case recorded no measurement while hidden, so an unchanged number either side proves less. Re-run it on the owner's display, through the product's own path, capturing the window: pause, collapse the stage, restore it, and measure saturation over the stage rectangle at **four** moments, not three — before, while hidden, after, and 1.5 s after that. The hidden sample is the one the original probe skipped and the one that makes the rest mean anything. Pass condition, on three runs out of three: hidden reads at or near the empty-shell floor, before and after both read at the video level, and after is within a few percent of before. The real-session check's own numbers are the scale to judge against — 2.1 empty against 5.86 with the frame up — so "near the floor" means within noise of 2.1 and "at the video level" means close to 5.86, not merely above it. The fourth sample separates a live picture from a frozen one only in the playing case; with the video paused it should be identical to the third, and a _drifting_ number there would mean something is redrawing that should not be. Decision 1's entire product behaviour rests on this, and the paused case is the one every open lands in (`player.rs:50`, `:269`).

**P3 — What are the two scale numbers on the 3840x2160 display at scale 1.5?** Read `window.devicePixelRatio` inside the webview and `window.scale_factor()` from Rust, both on that display, and print them. This is prerequisite to fixing N2c correctly rather than guessing, because the Linux path currently discards the scale factor entirely, and because `tao` stores the Linux scale factor as an integer fed from GTK, which cannot carry 1.5. If both report 1, the fractional factor has to come from somewhere else and N2c's stated fix is wrong. If they disagree, the disagreement is the bug.

**P4 — Do mouse events over the video rectangle reach React?** Open a video, click at the centre of `.stage__surface`, and count DOM events. Nothing in the code suggests they arrive and nothing tests it. This one needs synthetic input, so it runs under Xvfb and nowhere else (WORKFLOW §4c); the pieces already exist, `clickAt` from `e2e/lib/input.js` and the physical-pixel centre helper `video.spec.js:12` uses. The measurement is a counter incremented by a `pointerdown` listener on `.stage__surface`, read through `browser.execute` before and after: it needs a control, so click once with a video open and once on the same rectangle with no video open and the surface unmapped. Zero with the video open and non-zero without it is the expected result and the one that matters — it says the native window is eating the input. Non-zero in both means events do arrive and click-to-seek is available today. Zero in both means the listener or the click coordinates are wrong, not that input is blocked, and the probe is fixed before it is believed. If events do not arrive, click-to-seek and click-to-focus are foreclosed today, and that belongs in writing before M2.0 designs around it.

**P5 — Does the native close-gate dialog actually stack above a mapped video surface?** N1 was verified with no video loaded, and `shell-layout.md:282` already records this as an argument about window managers rather than a verified fact. It has to be answered on the owner's real compositor, because the claim under test is about a window manager and Xvfb has none worth the name — which means no keyboard and no clicks are available (WORKFLOW §4c). Both halves are reachable without them: pass the fixture on the command line the way `startup_files` allows, dirty nothing, and ask for the close with the same `closeWindowTool` message `wayland-attach-check.js:148` already sends, which is a WM close request and not synthetic input. Dirtying the document is the part that needs input, so run this one with an already-dirty document supplied at startup if that becomes possible, and otherwise accept that the gate cannot be raised on the real display and run it under Xvfb with the caveat written on the result.

Capture the toplevel with `import -window` and read the dialog's own rectangle out of `xwininfo`: the pass condition is that the region where the dialog overlaps the video rectangle reads as dialog chrome, not as colour bars, measured as saturation the way P1 does. If the dialog is behind the video, N1's chosen mechanism has a hole and decision 1's "native windows are outside the rule by construction" is wrong — and since native dialogs are exactly what N1 chose over HTML ones, that failure costs a shipped design decision, not just a test.

**P6 — Does shaping the surface clip mpv's own child window?** SHAPE is present on the owner's display (measured with `xdpyinfo` on `:0`). Cut a rectangular hole in the surface's bounding shape over a part of the stage where the page draws something identifiable, and capture the window. Two regions, same instrument as P1: **H**, inside the hole; **V**, the rest of the video rectangle. Pass condition on three runs out of three is V at the video level and H at the page level, with the two separated by the same margin P1 demands. H reading as colour bars is the failure that kills the idea: it means mpv's child window is not clipped by its parent's shape, so the hole is cosmetic and the middle path in §5 is not real. If it passes, that path is far cheaper than a migration, and it should be costed properly before condition 1 of §6 is ever exercised — which is why this probe ranks beside P1 rather than below it. Either way the answer arrives in an afternoon rather than in a milestone.

**P7 — What are cold start and idle memory today?** M16's own acceptance criteria demand a before-and-after comparison against the budgets in **CLAUDE.md §7** — under 2 s cold start to interactive, under 400 MB idle with a project open and the video paused — and no before-number exists anywhere in the repo. (Note the collision: "§7" in this document is the probe list you are reading; the budgets are CLAUDE.md's §7, and every mention of a budget in this document means that one.) Measure both on the owner's machine, five runs each: cold start as the interval from process spawn to the first frame of the shell being on screen, taken from the app's own log timestamps rather than a stopwatch, and idle memory as PSS from `/proc/<pid>/smaps_rollup` sixty seconds after the video is open and paused, since RSS over-counts shared library pages and would flatter the result. Report the median and the worst of the five, not the best. Without this, any future migration cannot be judged pass or fail on the budgets it most endangers, and neither can the current path.

**P8 — Does mpv call `get_proc_address` after `mpv_render_context_create` returns?** Only relevant if a migration is approved, and cheap: a callback that logs each resolution with a timestamp, one run. `libmpv2` frees the boxed init params as soon as create returns — `create_render_context` registers `free_init_params` as the deleter for `RenderParam::InitParams` and runs every registered deleter on the line after `mpv_render_context_create`, before the `RenderContext` is even constructed — while `render_gl.h:107-109` describes the callback as something mpv "will use in subsequent operation". If mpv resolves lazily, that free is a use-after-free waiting for a driver, and the crate needs patching before it is trusted.

**P9 — Can pixels be trusted anywhere in CI?** Before any assertion depends on them: run the existing saturation helper against a known-good and a known-empty window, twenty times each, on the CI display and on the owner's display. What is being measured is the instrument, not the app. A helper that cannot distinguish the two cases at 20 out of 20 is not an assertion, and a migration that depends on pixel assertions cannot start until one exists.

Probes P2, P3, P7 and P9 are worth running whichever way this decision goes — P7 belongs on that list because a budget with no before-number cannot be regressed or defended by either mechanism. P4 and P5 answer questions about the shipped product that are open today and would still be open if nothing changed. P8 is dead weight unless a migration is approved.

**P1 and P6 are the two that could change the decision, and P6 is the cheaper of them.** If P6 passes, the shaped surface buys some of what the render API was wanted for at a fraction of the cost, and P1's result then decides a smaller question than it does today. Run P6 first for that reason, not because it is more likely to pass.
